# FMS V2 ↔ V3 完整對照表——同一份需求，兩個世代的實作

> 教學用（2026-08-25）。兩版功能需求（FACT/TASK/PERS/ACC/EXCL）**編號完全相同**、
> Demo 劇本**同一份**、里程碑 M1~M6 **同一套骨架**——差異全部在「怎麼實作」。
> 本文供講師備課與學員課後對讀；各版細節以各自的 `docs/SRS.md` 為準。

---

## 1. 定位：為什麼要有兩版

| | V2 | V3 |
|---|---|---|
| 一句話 | **約定優於配置**的伺服端渲染世代 | **顯式契約**的型別安全全棧世代 |
| 適合先修 | 程式初學者第一個 Web 專案 | 已懂 HTTP/SQL 基礎，要學現代前後端分離 |
| 教學核心 | MVC、ORM、框架幫你做掉多少事 | REST 契約、型別安全、框架不幫你做的事要自己接 |

上完 V2 再做 V3，學員能親身回答一個工程史級的問題：
**「框架世代交替時，哪些東西變了？哪些東西（需求、口徑、安全原則）從來沒變？」**

## 2. 技術棧總表

| 面向 | V2 | V3 |
|---|---|---|
| 語言 | Python 3 | TypeScript（strict） |
| Runtime | CPython | Bun（runtime+套件管理+測試三合一） |
| Web 框架 | Django（MTV，伺服端渲染） | Elysia（REST API）+ Refine（SPA） |
| UI | AdminLTE 3.2（Bootstrap 4.6，template 渲染） | Ant Design 5（React 18 元件） |
| 資料庫 | SQLite（檔案型，Django 內建支援） | **PostgreSQL 17 伺服器**（Docker;映像內建 pgvector） |
| ORM / SQL | Django ORM（QuerySet） | 無 ORM——具名 SQL 模板（QueryTemplate，TS+Zod） |
| 表單/驗證 | Django Forms + model `clean()` | Elysia `t`（路由層）+ Zod（服務層）雙層 |
| 認證 | Django session（cookie） | JWT（jose）存 httpOnly cookie |
| 密碼雜湊 | Django 內建（PBKDF2 預設） | `Bun.password`（argon2id） |
| 權限 | Django auth groups/permissions + admin | Refine `accessControlProvider` + 後端角色守衛 |
| 測試 | Django `TestCase`（測試資料庫自動建拆） | `bun test` + 每檔獨立 PG schema |
| 靜態資產 | `static/lib/` vendor（AdminLTE/jQuery/字型） | npm 套件由 Vite 打包（天生無 CDN） |
| 交付部署 | Docker Compose 單服務（web + SQLite volume） | Docker Compose **三服務**（nginx 反代 `/api` + backend + **db**；PG 具名 volume、healthcheck 等待） |
| Lint/格式 | flake8/black（慣例） | Biome（單一工具） |
| CI | （課程選配） | GitHub Actions：install→typecheck→test |

## 3. 一個請求的生命週期（最重要的概念差異）

**V2（伺服端渲染）**：
```
瀏覽器送 <form> POST
  → urls.py 路由 → view 函式（驗證 Form → ORM 寫入）
  → 整頁 template 重新渲染 → 回傳完整 HTML
```
狀態活在伺服器（session）；瀏覽器只是顯示器。學到:請求-回應循環、CSRF token 為何存在。

**V3（前後端分離）**：
```
React 元件 fetch /api/tasks（vite proxy → Elysia 3000）
  → 路由層 t 驗參+JWT 解析+角色守衛 → service（業務檢核）
  → SQL 模板（參數化）→ pg 連線池 → PostgreSQL → 回 JSON
  → Refine dataProvider 更新畫面（局部重繪）
```
狀態分兩邊（前端 UI state / 後端資料）；契約=REST+JSON。學到:API 設計、CORS/cookie、
前後端各自要驗一次的原因。

## 4. 核心需求逐條對照（同一條需求，兩種解法）

| 需求 | V2 解法 | V3 解法 | 不變的原則 |
|---|---|---|---|
| PERS-4 管理介面 | Django admin：註冊 model 即得 CRUD（**約定即得**） | Refine resources + Inferencer 生成頁 + `accessControlProvider` 擋權限（**顯式接**） | 只有 Admin 進得去;後端守衛才算數 |
| TASK-3/4 能力/證照匹配 | model `clean()` 或 service 函式；Form 驗證呈現錯誤 | `services/scheduling.ts` 純函式（可單測）；400 帶人話訊息 | 業務規則不可只做在 UI 層 |
| TASK-6 排程不重疊 | 應用層查詢檢查 + **DB unique constraint 保底** | 服務層檢查 + **PG `EXCLUDE USING gist` 保底**（並行測試必做） | 應用層檢查有 race，資料庫約束才是底 |
| FACT-2 ISO 週次 | `date.isocalendar()`（內建，一行） | 自寫 `isoWeek()` 工具 + 先寫測試（12/31、1/1、閏年） | 第 53 週、跨年週是必考陷阱 |
| PERS-15 CSV 匯入 | Django view + `csv` 模組;Form 報錯 | papaparse + Zod 逐列驗證;錯誤列號回報 | 編碼要偵測（Excel=CP950）;半途失敗要交代清楚 |
| PERS-24 匿名化 | **queryset 層**就不取真名（`annotate` 別名） | **SQL 層** `dense_rank()` 出別名（模板見 V3 SRS 2.1.7） | 在顯示層藏名字＝沒藏;資料離開資料層前就要匿名 |
| TECH-9 安全 | CSRF token（Django 內建）+ ORM 天然參數化 + login_required | SameSite cookie + `$n` 參數化 + JWT 守衛 | 注入靠參數化、越權靠伺服端守衛，兩版同理 |
| ACC-4 千筆效能 | ORM `select_related` 防 N+1;必要時加 index | SQL 模板直接寫 JOIN;必要時加 index | 慢查詢的根因（N+1、缺索引）與框架無關 |
| TECH-12 離線 | `static/lib/` vendor 全套 + **uv** wheelhouse（`uv.lock` 鎖版） | Vite 全打包 + bun offline 快取 | 斷網驗收（ACC-6）;字型一律系統字型堆疊 |

## 5. RBAC 對照（詳見各版 SRS）

| Django 概念 | V3 對應 | 備註 |
|---|---|---|
| `User.groups` / `is_staff` | JWT payload 的 `role` | 角色定義同一份（Admin/Site Manager/Operator/Anonymous） |
| model permissions（add/change/delete/view） | `accessControlProvider.can({resource, action})` | V3 的 can=false 會自動藏選單/禁按鈕/擋路由 |
| `@login_required` / `PermissionRequiredMixin` | Elysia 路由守衛（middleware） | **兩版鐵律相同：前端/模板擋 UX，後端擋安全** |
| admin site | Refine admin 資源頁 | 權限矩陣同一張（見各版 SRS 2.1.4／2.4） |

## 6. 資料層對照

| | V2 | V3 |
|---|---|---|
| Schema 管理 | Django migrations（`makemigrations`/`migrate`） | 冪等 `schema.sql`（`CREATE TABLE IF NOT EXISTS`，啟動即建） |
| 查詢 | ORM QuerySet（框架生 SQL） | 具名 SQL 模板（人寫 SQL，`name+source+sql+params`） |
| 溯源 | —（ORM 查詢散在 view/service） | 每條模板 `source:` 指回 SRS 需求編號（需求↔SQL 雙向可追溯） |
| 測試隔離 | Django 測試資料庫（框架自動建拆） | 每個測試檔開自己的 PG schema（跑完 DROP） |
| 教學價值 | ORM 的生產力與 N+1 陷阱 | SQL 是資產：參數化、window function、約束當防線 |

## 7. 何時選哪個（給學員的職涯視角）

- **V2 路線**擅長：後台/內部系統快速交付、團隊小、需求以表單+清單為主——Django admin
  一天能做出別人一週的量。代價：UI 客製到某個程度會開始「跟框架打架」。
- **V3 路線**擅長：產品級前端體驗、多端（Web/App 共用 API）、團隊前後端分工——契約清楚、
  型別從 DB 到畫面連通。代價：所有「框架幫你做的事」都要自己接，起步成本高。
- **不變的判準**：需求編號那一層（業務規則、權限矩陣、口徑）與框架無關——
  這正是本課程用同一份 SRS 做兩版的原因。

## 8. 常見誤解澄清

1. 「V3 比較新所以比較好」——**錯**。兩版是取捨不是優劣;第 7 節的場景判準才是答案。
2. 「Django admin 有了就不用寫權限」——**錯**。admin 外的 view 一樣要守（V2 附錄 B 坑 6）。
3. 「前端擋掉按鈕就安全了」——**錯**。兩版同一條鐵律：後端守衛才是防線。
4. 「SQLite 是玩具」——課程規模（千筆任務）下綽綽有餘;
   嵌入式資料庫換來的是**零安裝離線教室**（TECH-12/ACC-6），這是刻意的工程取捨。
